# 依頼文テンプレート

振り分け先ごとの整形テンプレ。**依頼文単体で完結させる**のが原則
（特にCodexはトリアージ時の会話文脈を一切持たない）。
角括弧 `[ ]` の部分を埋めて出力する。埋められない項目は削らずに「要確認: 〜」と残す。

## Claude向け

```
## 依頼

[やってほしいことを1〜2文で]

## 背景

[なぜやるのか。依頼元（大統領）の意図も補完して書く]

## 成果物と完了条件

- 成果物: [何ができたら完了か]
- 完了条件: [品質基準・受け入れ条件]
- 期限: [あれば]

## 使うもの

[コネクタ名・Skill名・対象リポジトリなど。例: Slack #channel-name、Notion「◯◯」DB]

## やらないこと

[スコープ外を明示。例: 本番への反映は人間の承認後]
```

## Codex向け

```
## Task

[やってほしいことを1〜2文で]

## Context

[リポジトリ名・ブランチ・関連ファイルパス。会話の文脈は持っていない前提ですべて書く]

## Deliverables & Acceptance Criteria

- [成果物]
- [完了条件。テストがあるなら実行コマンドを明記: 例 `python3 scripts/verify.py` が通ること]

## Out of Scope

[やらないこと。例: 依存パッケージの追加、既存APIの変更]
```

## クロスレビュー向け（2通セット）

### 実装側への依頼文

上の Claude向け / Codex向け テンプレをそのまま使う。ただし末尾に追記：

```
## 補足

この変更は別ツールによるレビューを通してからマージする。
レビューしやすいよう、変更理由をコミットメッセージ / PR説明に書くこと。
```

### レビュー側への依頼文

```
## Task

[リポジトリ名] の [ブランチ/PR] をレビューしてほしい。実装は別ツールが行った。

## 変更の背景

[元タスクの目的と完了条件を再掲]

## レビュー観点（すべて確認すること）

1. 仕様充足: 完了条件を満たしているか
2. 破壊的変更: 既存の動作・データを壊していないか
3. セキュリティ: 認証・入力検証・秘匿情報の扱いに問題がないか
4. テスト: テストは妥当か。通っているか

## 出力

観点ごとに OK / 要修正 を明示し、要修正は該当箇所と修正案をセットで書くこと。
「なんとなくLGTM」は禁止。
```
