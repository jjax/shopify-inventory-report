# 振り分けルーブリック v0.1（たたき台）

使い方: **R1から順に評価し、最初にマッチしたルールで判定する。**
このファイルが判断の本体。判定が外れたらここを直す（スキル本体は直さない）。

## 分岐表

| # | 条件 | 判定 | 理由 |
|---|------|------|------|
| R1 | Slack / Notion / Intercom / Gmail / カレンダー / バクラク / Claude in Chrome など、Claude側のコネクタ・既存Skillを使う業務タスク | **Claude** | Codexはこのハーネス資産（コネクタ・Skill・Memory）に触れない |
| R2 | 本番環境への変更、不可逆な操作、金額、社外公開物が絡むコード変更 | **クロスレビュー** | 単独実行のリスクが高い。片方が実装し、もう片方がレビューする |
| R3 | セキュリティ・認証・決済まわりの変更 | **クロスレビュー** | R2と同じ。レビュー観点にセキュリティを必ず含める |
| R4 | リポジトリ内で完結する純コーディング（実装・テスト反復・リファクタ等） | 実績表を参照。実績が無ければ **Codex（仮置き）** | どちらも得意な領域。実績データで更新する前提のデフォルト |
| R5 | 調査のみ・書き捨てスクリプト・ワンショットの分析 | **どちらでも可**（今すぐ使える方・速い方） | 失敗コストが低いので振り分けに悩む価値がない |
| R6 | 上記いずれにも該当しない、または情報不足 | **人間確認** | 誤配のコスト > 確認のコスト |

> **注意（要調整）**: R4のデフォルト「Codex」は根拠のない仮置きです。
> 最初の2〜3週間の実績表を見て、Claudeに変える・タスク種別ごとに分ける等、必ず見直すこと。

## 実績表（運用しながら育てる）

判定の答え合わせに使う。「同じ種類のタスクをどちらに投げたら何が起きたか」を貯める。

| 日付 | タスク種別 | 実行先 | 結果（成功 / やり直し / 失敗） | メモ |
|------|-----------|--------|------|------|
| （記入例）2026-08-15 | Pythonスクリプトのバグ修正 | Codex | 成功 | テストまで自走した |

## クロスレビューの型

- **実装**と**レビュー**を別のツールに割り当てる（例: Codexが実装、Claudeがレビュー）。
  どちらを実装側にするかはR4と同じ基準（実績表→仮置き）で決める。
- レビュー観点: ①仕様充足 ②破壊的変更の有無 ③セキュリティ ④テストの妥当性
- **並列に両方実装させて比較する方式は原則使わない。**
  高コストな割に、比較・統合の判断が結局人間に戻ってくるため。

## 更新ルール

- 同じルールで**2回連続**判定が外れたら（やり直し・誤配）、そのルールを修正する。
- 見直しは harness-audit の週次監査に乗せる。`triage-log.md` の「ルーブリック修正要否」列が入力になる。
- ルールの追加・変更をしたら、このファイル冒頭のバージョンを上げて変更内容を下に追記する。
